# ADR-0008: 易用性与轻量同等重要；对标纪律 D18

| 状态 | 日期 | 关联 |
|---|---|---|
| 已接受（元裁决） | 用户直裁 2026-09-20；修订 2026-09-23；收录 2026-09-29 | [v0.2 规划](../plan/2026-09-20-v0.2-plan.md)（红线 1）、[架构](../design/2026-09-17-architecture.md)（D18/FZ-9） |

## 背景

轻量 PaaS 的架构取舍遇到「轻量 vs 易用」冲突时往哪边倒——这是所有组件引入决策的上位裁决。

## 决策（用户直裁）

1. **易用性与轻量要求同等重要：「只轻量但不好用就没有意义」**；内存限额可以适当提高（当次决定：平台 idle 预算 400MB→600MB）。
2. **600MB 门只管辖默认捆绑面**（2026-09-23 修订）：opt-in 组件不占顶，启用态如实记录不设顶。
3. **红线对象是「多容器重栈」**：fluentd+Loki+Grafana 三件套、Temporal 级引擎这类仍然禁止。
4. **允许的引入形态**：单二进制+控制面直推、无采集中间层的轻组件，以**实测门**约束引入（FZ-9 先测再定）。
5. **对标纪律 D18**：Dokploy 体验为地板、Cloudflare 为方向；**Dokploy 没有且无硬承诺的机制一律不做**。
6. 预算不够时优先「实测校准+降级路径」，不优先「直接砍易用性」。

## 后果

- 这是元裁决：评审任何「为省内存砍能力」或「为体验上重栈」的候选都先过这条。
- 自建 keepalived+haproxy 类方案被本裁决+ADR-0005 联合否决。
