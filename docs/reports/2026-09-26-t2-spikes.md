## 1. Spike ①：Docker 29 internal overlay 出网实证（DT-7）

**run-id**：单节点矩阵 `20260927-104155-s1-host`；跨节点腿 `20260927-110207-s1-cx`。
脚本：`spike/t20/scripts/s1-host-overlay-matrix.sh`、`s1-cross-node-overlay.sh`（+ `in-overlay-probe.sh`、
`in-cx-service-probe.sh`）。

### 1.1 方法

语义矩阵四格（单节点宿主，Docker 29.7.2）：`bridge`（基线）/ `bridge --internal`（对照组，
现役「无 NAT 全 deny」语义）/ `overlay --attachable`（基线）/ `overlay --attachable --internal`
（被测）。每格两个容器（peer 跑 busybox nc 监听 8080，probe 主动探测），测：

- 对等面：`nslookup <peer>` / `ping` / `nc <peer> 8080`；
- 公网面：`nslookup example.com`、`nc 1.1.1.1:80`、`nc 8.8.8.8:53`、`wget http://1.1.1.1/`；
- 路由证据：`/proc/net/route`、`/etc/resolv.conf`、网卡清单、失败原文。

跨节点腿（双 dind `29.8.1`，host bridge 10.240.0.0/24 上 mgr+w1 组 swarm）对
`overlay internal`（被测）与 `overlay`（基线）各两层：L1 = attachable 容器跨节点互测；
L2 = `--mode global` 服务两任务，`tasks.<svc>` 跨节点 DNS 发现 + 逐地址 ICMP。

### 1.2 原始数据

单节点矩阵（`s1-host-summary.txt`，节选）：

| 格 | 路由表（目的网络→网关） | 网卡 | 对等 DNS | 对等 TCP | 公网 DNS | 公网 TCP:80 | 公网 HTTP |
|---|---|---|---|---|---|---|---|
| bridge | `00000000->010014AC`（默认走 172.20.0.1） | eth0,lo | ok | ok | ok | ok | ok |
| bridge internal | 仅 `000014AC`（172.20.0.0/16，**无默认路由**） | eth0,lo | ok | ok | **fail** | **fail** | **fail** |
| overlay | `00000000->0110A8C0`（默认走 docker_gwbridge 192.168.16.1） | eth0,eth1,lo | ok | ok | ok | ok | ok |
| **overlay internal** | 仅 `0001000A`（10.0.1.0/24，**无默认路由/无网关**） | **eth0,lo（无 gwbridge eth1）** | **ok** | **ok** | **fail** | **fail** | **fail** |

internal 格失败原文（`s1-host-ov-in.log`）：
`HTTP_PUBLIC_OUT=wget: can't connect to remote host (1.1.1.1): Network unreachable`；
`DNS_PUBLIC` = `** server can't find example.com: SERVFAIL`；
对等面 `DNS_PEER_ADDR=10.0.1.2`、`PING_PEER 0% packet loss`、`TCP_PEER=ok`。
`docker inspect` 网络属性：internal overlay 容器 `Gateway=""`、单网段 10.0.1.0/24；
非 internal overlay 容器多一个 docker_gwbridge 接口（eth1）与默认路由。

跨节点腿（`s1-cx-summary.txt` + `s1-cx-ov-in.log`）：

| 面 | overlay internal（被测） | overlay（基线） |
|---|---|---|
| L1 容器↔容器（mgr↔w1） | 双向 `DNS_PEER=ok`（解析到对端 overlay IP 10.0.1.4 / 10.0.1.2）、`TCP_PEER=ok`；路由仅 10.0.1.0/24、单网卡 | 双向 ok；有默认路由/双网卡 |
| L1 出网 | `DNS_PUBLIC=fail`、`TCP_PUBLIC_80=fail`、`HTTP_PUBLIC=fail`（Network unreachable） | 全部 ok |
| L2 服务任务（global，2 任务） | 两任务均 `SVC_TASKS_DNS=ok`（发现 2 个任务地址 10.0.1.7/10.0.1.8）、`SVC_PING_1/2 ok`；出网 fail | 出网 ok |
| L2 镜像拉取 | 任务正常 Running（镜像由 agent 在**节点侧**拉取，不依赖容器出网） | 同 |

### 1.3 结论

1. **internal overlay 出网：封死，与 bridge internal 语义对齐**。证据三重一致：
   无默认路由 + 无 docker_gwbridge 接口 + 公网 DNS/TCP/HTTP 全部失败（`Network unreachable` /
   `SERVFAIL`），而对等 DNS/ICMP/TCP 全部正常。矩阵中两个 internal 格（bridge/overlay）在
   出网面上逐项同构，两个非 internal 格逐项同构。
2. **跨节点 internal overlay 的 DNS/数据面正常**：attachable 容器双向名字解析与 TCP 连通；
   swarm service 任务（global，两节点）能解析 `tasks.<svc>` 到两个任务地址且双向 ICMP 通
   ——internal 只影响**对外**连通，不影响 overlay 数据面。
3. **DT-7 的可信条件成立**：以 `--internal` overlay 承接不可信函数隔离，不需要触发
   「宿主 nft 兜底」分支（该兜底方案仍保留为 staging 真机复核不通过时的运维后备，见 1.4）。
4. 附注：镜像拉取发生在 swarm **agent/daemon 侧**（节点网络命名空间），internal 网络不阻塞
   镜像分发——internal 网络上的任务照常启动（实测两节点任务均 Running）。

### 1.4 对设计的影响（确认 / 修正建议）

- **确认 DT-7**：`overlay internal` 变体可以作为 Tasks API 的不可信隔离面；DT-5 的
  「internal 变体承不可信函数」无需降级。
- **修正建议（运维/文档，非代码）**：
  1. 文档写明 internal 语义 = 无出网 + **无外部 DNS**（应用若需解析公网域名会失败，属预期）；
  2. 平台侧创建 internal 网络时保持一致参数（`--driver overlay --internal`；
     attachable 仅调试用），并把「不 attach 默认网关」作为验收点写进 T2-1 守卫；
  3. **宿主 nft 兜底方案（仅在 staging 复核不通过时启用）**：按网段封 egress 的可执行形态——
     对 internal 网段在宿主 filter 表 forward 链加
     `ip saddr <internal 子网> ip daddr != <internal 子网> drop`（IPv6 同构），与安装器/加固
     脚本的衔接点 = `deploy/install.sh` 的宿主加固段；验收方式 = 用本 spike 的探针脚本在目标
     宿主重跑，断言 `TCP_PUBLIC_*`/`HTTP_PUBLIC` 全 fail 且 `TCP_PEER` ok。本轮未触发该分支。

### 1.5 不确定性

- 本机 dind/宿主 docker 的 overlay 实现与真实云 VPC 网络设备不同——**UDP 4789/7946 是否被云
  安全组过滤**是 staging 才能回答的问题（design §5 已列 T1.5 前置运维动作）。
- 单节点矩阵在宿主 29.7.2 上跑，跨节点在 29.8.1 dind 上跑；两版本行为一致，但 29.x 次版本
  间无全矩阵对照。
- 服务任务层出网只测了 `DNS_PUBLIC`/`TCP_PUBLIC_80`（`in-cx-service-probe.sh`），未测 HTTP
  wget（与 L1 结论一致，风险低）。

## 2. Spike ②：digest registry 直拉真机（T1-2 必查项的真机腿）

**run-id**：解析腿 `20260927-121944-s2-resolve`；跨节点+凭证腿 `20260927-133343-s2-dind`
（复跑样本 `20260927-132411-s2-dind`、`20260927-132027-s2-dind`，见 §8）。
脚本：`spike/t20/scripts/s2-resolve-digests.sh`、`s2-digest-auth-dind.sh`；
探针：`spike/t20/cmd/t20resolve`（生产 `internal/imageregistry` 客户端）。

### 2.1 方法

三条真机腿 + 一条边界探针（脚本见上；全部可复跑）：

1. **解析腿（生产代码真机）**：`FLEETLY_MANUAL_REGISTRY=1 go test -tags manual
   ./internal/imageregistry -run TestManualResolvePublicRegistryImages -v`——Docker Hub 匿名
   Bearer token flow + ghcr 匿名 flow；并用 `spike/t20/cmd/t20resolve`（同一生产客户端）打印
   显式解析行。
2. **零预拉部署腿（本机单节点）**：`FLEETLY_MANUAL_SWARM=1 go test -tags manual
   ./internal/substrate -run TestManualPublicImageZeroPrePull -v`——T1-2 手跑探针原样复跑：
   清场本机镜像 → `substrate.ImageDigest` registry-first 解析 → digest 钉定建服务 → 任务真拉。
3. **跨节点 + 凭证腿（双 dind swarm + 本地 registry:2/htpasswd）**：
   - **A**：`alpine:3.19` 经生产 resolver 解析 → `--mode global` 两任务 digest 钉定引用；
     创建前两节点按 digest 引用 inspect 均不存在（零预拉），创建后查两节点 dockerd
     `image pulled` 行 + digest 引用 inspect。
   - **B**：`registry:2` + htpasswd Basic Auth 私有仓库；mgr 推 `t20/private:1`（alpine:3.20
     基座）与 `t20/private:2`（`LABEL` 变体 → 新 manifest digest，强制真拉新 manifest）；
      - **B2 对照**：不携 auth 建服（约束 w1）→ 预期 401 拒绝；
      - **B1 携 auth**：`docker service create --with-registry-auth`（= API `EncodedRegistryAuth`
        下发的 CLI 等价形态；w1 无任何本地 docker login）→ 预期 w1 真拉成功；
      - **B3 update 不携 auth**：`docker service update --image <tag2>`（**不带**
        `--with-registry-auth`）→ 新任务在 w1 拉取全新 manifest → 验证 spec 内 PullOptions
        凭据在 update 后留存；
      - **B4 披露面**：`docker service inspect` 原文（落 `s2-inspect-auth.json`）核零凭据；
      - **存储面**：dind 内 swarm raft 目录形态与明文凭据检索（用户名 + 平台口径
        X-Registry-Auth 编码 blob）。
4. **边界探针**：生产 resolver 对纯 HTTP registry 的行为（HTTPS-only 设计面）。

### 2.3 结论：与 T1-2 已有结论的一致性 / 增量 / 分歧

- **复核确认（与 T1-2 一致）**：
  1. tag→digest 解析（Docker Hub/ghcr 匿名 token flow）真机可用，digest 与 T1-2 记录逐字一致；
  2.「解析失败 → 本机 inspect 回落」的 airgap 语义未见回归（手动探针全链过）；
  3. `EncodedRegistryAuth`：**create 携 auth → 写入 spec；update 不携 → 凭据不丢**（T1-2
     审查源码结论的真机腿首次以「update 后换新 tag、w1 无本地登录仍真拉成功」钉死）；
  4. 披露面：inspect API 不回显 PullOptions/RegistryAuth（本轮再次实测）；raft 静态加密
     （`*-encrypted`）且明文不可检索。
- **新增证据（本票增量）**：
  1. **逐节点 digest 直拉**：同一 digest 引用在两个 dind 节点各自真拉成功（零预拉），
     拉取发生在节点侧、与容器网络出网能力无关——「Docker29 离线预拉坑位（digest 不落 tag /
     save-load 丢 tag）不影响 registry 直拉路径」在本口径成立（本轮全程无 save/load）；
  2. **私有镜像 + Basic Auth 全链**：本地 registry:2 + htpasswd 构造下，B1/B3 的 w1 拉取、
     registry 侧逐请求日志、401/200 挑战应答全链可查；
  3. 复跑可重复（三次运行计数一致）。
- **分歧**：无。两处**设计面/环境面补充**（非分歧）：
  1. 生产 resolver **只讲 HTTPS**（`internal/imageregistry` 无 scheme 逃逸面）——纯 HTTP
     私网 registry 解析必然失败；本轮以私网 registry 实测钉住该边界（错误清晰、随即回落）。
  2. dind 的 containerd image store 下，**agent 拉取的镜像不出现于 `docker image ls`**，
     而按 digest 引用的 `docker image inspect` 在任务运行后可见（见 §7.4）。

### 2.4 对设计的影响

- **确认 DT-2 / T1-2 实现**：registry-first 解析 + digest 钉定 + 凭证随 spec 下发 + 逐节点
  直拉，四项在真机（含私有镜像）全部成立；T2-1（Tasks）与 T2-2（build-from-upload 产物
  digest 引用）建立在此结论上，无修正需求。
- **建议（文档/运维面）**：
  1. 在 registry 设置文档写明「仅 HTTPS registry」（HTTP 需自行加 TLS；平台 zot 路径不受影响）；
  2. 在 image-prepull runbook 补一句：平台部署路径**不需要**离线预拉（digest 直拉），
     预拉仅服务 airgap/加速场景；
  3. T1-2 的两条 staging 真机项（ghcr 多节点零预拉、平台设置凭证逐节点）仍按 §5 待
     staging 复核（本 spike 的 dind 形态是它们的本地同构，不替代）。

### 2.5 不确定性

- 无 staging 访问权：真实云跨宿主网络的逐节点拉取、平台设置面（envelope 加密 + 立即生效）
  未在 staging 验证（§5 第 2/3/4 项）。
- 私网 registry 场景用 **CLI `--with-registry-auth`** 作为 API `EncodedRegistryAuth` 的等价
  形态（平台代码路径的编码/下发已有 T1-2 单测 + 披露面探针；本轮验证的是服务端语义）。
- 私有 registry 为 HTTP（dind 以 `--insecure-registry` 接受）；真实 HTTPS registry 的
  证书链行为未覆盖（属 staging/用户环境面）。


## 3. Spike ③：swarm service 生命周期时延基线

**run-id**：默认停机宽限 `20260927-113938-s3`；有界 2s 宽限 `20260927-120331-s3`。
脚本：`spike/t20/scripts/s3-lifecycle-latency.sh`、`in-lifecycle-latency.sh`、`s3-stats.sh`。

### 3.1 方法

单 dind（29.8.1，`docker swarm init` 单节点）内，全部时间戳取 `docker events` 的
`TimeNano`（同 daemon 时钟），不取轮询墙钟；N=30 每臂：

- **Arm A（swarm service）**：`service create --detach`（restart-condition none，
  `--health-cmd true --health-interval 1s`）→ 任务容器 `start`/`health_status: healthy`
  → `service update --force -d` → 新任务容器 healthy → `service rm` → 容器 `die`/`destroy`。
- **Arm B（docker run/stop 直操）**：`docker run -d`（同 healthcheck）→ `docker stop -t <grace>`
  → 容器 die/rm。这是 torchwood dispatcher 现役形态（`ContainerCreate`+`ContainerStart`，见
  `D:/Codes/qiulin/torchwood/dispatcher/daemon.go`）的等价基线。

两配置：①默认停机宽限（10s；`sleep` 作为 PID 1 忽略 SIGTERM，宽限全量计入）；②
`--stop-grace-period 2s` / `docker stop -t 2`（隔离控制面时延）。分布统计见 `s3-stats.sh`。

### 3.2 原始数据

Arm A（swarm service，ms；n=30）：

| 指标 | 默认 10s 宽限 run 113938 | 有界 2s 宽限 run 120331 |
|---|---|---|
| create→task running | 389 / **406** / 420 / 445 | 387 / **406** / 425 / 479 |
| create→healthy | 1417 / **1431** / 1447 / 1471 | 1413 / **1432** / 1451 / 1516 |
| update→new task running | 11617 / **11698** / 11721 / 11752 | 3606 / **3678** / 3727 / 3745 |
| update→new task healthy | 12643 / **12725** / 12747 / 12778 | 4632 / **4707** / 4755 / 4772 |
| rm→task destroy | 11712 / **11747** / 11789 / 11808 | 3698 / **3762** / 3801 / 3843 |
| rm→task die | 11261 / **11311** / 11325 / 11339 | 3275 / **3314** / 3332 / 3356 |

（每列 = min / **p50** / p90 / max。原始：`s3-stats.txt`、`s3-metrics.txt`、`s3-events.log`。）

Arm B（docker run/stop 直操基线，ms；n=30）：

| 指标 | 默认宽限 run 113938 | 有界 2s 宽限 run 120331 |
|---|---|---|
| create→running | 131 / **143** / 158 / 169 | 128 / **144** / 156 / 189 |
| create→healthy | 1158 / **1169** / 1185 / 1194 | 1154 / **1171** / 1186 / 1215 |
| start→die（stop 生效） | 11221 / **12245** / 12267 / 12282 | 4210 / **4243** / 4259 / 4273 |

判读要点：

- **swarm 负载的控制面开销 ≈ 0.26s**（create→running：service p50 406ms vs run p50 144ms）。
- 健康门 p50 ≈ 1.43s，几乎完全是 1s healthcheck interval 的量化（容器侧 run 臂 p50 1.17s）。
- **停止宽限是回收时延的主导项**：`sleep`（PID 1，忽略 SIGTERM）在默认 10s 宽限下，
  update→new task running p50 ≈ 11.7s、rm→destroy p50 ≈ 11.7s；把宽限压到 2s 后，
  同样链路 p50 ≈ 3.7s（= 宽限 2s + **控制面/停机编排 ~1.7s**）。
- 崩溃/替换语义：`--force` update 走 stop-first（旧任务 die 后新任务起），
  `service rm` 后任务 die→destroy 有 ~0.4s 间隔（11311→11747 于默认宽限下）。

### 3.3 结论与对 DT-5/janitor 参数的修正建议

1. **余量结论：充足**。Torchwood dispatcher 现役池模型单实例生命周期为**分钟级**
   （池语义：租约/保温/熔断、`TW_MAX_REQUESTS` 自退），而 swarm service 承载的
   一次 spawn（create→healthy）**p50 ≈ 1.4s、p90 < 1.6s**；回收（rm→任务消失）
   在默认宽限下 p50 ≈ 11.7s、有界 2s 宽限下 p50 ≈ 3.8s。相较分钟级生命周期，
   控制面开销 <5%。Tasks 高频 spawn/回收无时延风险。
2. **TTL/janitor 参数建议**：
   - janitor 扫描周期 30s 量级对 TTL 精度影响可忽略（最坏多活 ≤1 扫描周期）；
   - task TTL 的推荐下限 **≥1 分钟**（低于此值会让「创建→健康→回收」的总开销
     与存活期同量级）；若 T2-1 要给默认 TTL，建议 5-15 分钟并暴露 owner 覆盖；
   - 回收时延预算 = `stop_grace` + ~1.7s 控制面。若平台统一给 task
     `stop_grace_period`（建议显式钉 2-10s，别留 daemon 默认语义漂移），
     回收可在「TTL 到期后 ≤10s 内」收敛；
   - 注意含卷/固定端口的服务会被规划为 stop-first（本时延臂同构），其回收
     含停机账，janitor 的窗口要覆盖它（30s 周期足够）。
3. **不确定性**：dind 单宿主环境（WSL2 内核）时序≠staging 真机；1s healthcheck 量化
   使「健康门」指标只有 ~0.1s 分辨率；N=30 的 p90 是分位点估计（非精确）；宿主 29.7.2
   与 dind 29.8.1 未做全矩阵对照。

## 4. Spike ④：多服务编排顺序语义观测

**run-id**：主样本 `20260927-133032-s4`；对照样本 `20260927-131347-s4`（同夹具复跑，失败场景
触发了另一条安全网——见 4.2）。脚本：`spike/t20/scripts/s4-ordering-dind.sh` + `in-s4-ordering.sh`；
fixture：`spike/t20/fixtures/ord{1,2,3}-*.yaml`。

### 4.1 方法

宿主交叉编译 fleetlyd+fleetly（linux/amd64）→ 单特权 dind 内 `swarm init` → fleetlyd 起服
（**加速参数**：`deploy_timeout=60s / observe=5s / replicas_below=5s / poll=1s`；平台默认是
300/60/10/**2**s）→ curl helper 注册 founder + 铸机具令牌 → dind 内 `fleetly deploy` 三组
fixture，同时采集：dind 内 `docker events`（TimeNano）、1s 粒度 `docker service ps` 快照、
`fleetly deployments list --json`、引擎事件流、fleetlyd 日志。三场景：

1. `ord1`：base→mid→leaf 依赖链。base 8s 后就绪（nc 监听 8080，healthcheck = `test -f /tmp/ready`）；
   mid 先探测 base 的 8080，不成就 `exit 1`（swarm 默认 restart=any 自愈）；leaf 同理依赖 mid。
2. `ord2`：good（立即健康）+ bad（`exit 1` 永久失败），观测健康门/看门狗判定与失败形态。
3. `ord3`：compose `depends_on: service_healthy` 的现行口径（本地 `fleetly validate`）。

### 4.2 原始数据

场景 3（`s4-report.txt` L1-6）：
`validate-rc=1` →
`E_COMPOSE_UNSUPPORTED: service "mid" uses an unsupported field "depends_on": rejected field in v0.1 (orchestration order is managed by the platform release pipeline)`，
`path: services.mid.depends_on`。

场景 1（ord1，事件解析 + 部署 JSON；主样本 133032）：

| 服务 | create 事件（相对最早） | create→容器 start | create→healthy | 容器 start/die（至首次 healthy） |
|---|---|---|---|---|
| base | +0ms | 1334ms | 9545ms | 1 / 0 |
| leaf | +11ms | 1138ms | 19689ms | 4 / 3 |
| mid | +22ms | 1070ms | 13754ms | 3 / 2 |

部署时间线（事件流 + deployments JSON）：`queued/release_started 13:31:04` →
`healthy/switched/observe_started 13:31:24`（首拍全服务 running/healthy）→
`succeeded 13:31:30`；CLI rc=0（墙钟 27s）。快照证实三服务容器同期 Starting，
mid 在 base 未就绪前 Failed 2 次、leaf Failed 3 次后自愈。

场景 2（ord2，永久失败服务）——**两次复跑各触发一条安全网**：

| 样本 | 时间线 | 失败码 | 容器计数 | 终态 |
|---|---|---|---|---|
| `133032`（主） | created 13:31:34 → healthy/切流 13:31:42（8s）→ failed 13:31:48 | `E_OBSERVE_UNHEALTHY`（副本水位不足） | good 1/0；bad 3 starts/3 dies | app degraded；good 1/1、bad 0/1 |
| `131347`（对照） | created 13:14:47 → healthy/切流 13:15:46（58s）→ failed 13:15:52 | `E_OBSERVE_CRASH_LOOP`（窗内 ≥2 次退出） | good 1/0；bad 12 starts/12 dies | 同上 |

CLI 原文：`deployment … failed: E_OBSERVE_UNHEALTHY ()` / `… E_OBSERVE_CRASH_LOOP ()`。
引擎语义（源码核对 `internal/engine/observing.go`）：观察窗崩溃判定 = **≥2 次退出**（只统计
`first_healthy_at` 切流点之后），另有副本水位 `E_OBSERVE_UNHEALTHY`（running < desired 持续
≥`ReplicasBelowFor` 或窗末不足）与单次退出自愈 `W_DEPLOY_INSTABILITY` 警告；默认参数
（`internal/engine/ports.go:361-380`）：DeployTimeout **300s**、ObserveWindow **60s**、
ReplicasBelowFor **10s**、PollInterval **2s**。两次复跑的差异（58s vs 8s 过健康门、
CRASH_LOOP vs UNHEALTHY）来自抽样式健康门与重启任务状态的时间竞速——机制不变，
表现随采样时点变化。

### 4.3 结论：顺序 or 并行 + 自愈窗口？

**诚实的结论：并行创建 + swarm 自愈 + 整组「与」健康门 + 观察窗兜底；平台不提供顺序语义。**

1. **创建是并行的**：三服务 create 事件间隔 0/11/22ms（同一次 `applyDesired` 扇出），容器
   start 在 ~1.1-1.3s 内全部发起；没有「先 base 起完再起 mid」的机制。
2. **依赖未就绪 = 应用侧崩溃 + swarm 重启自愈窗口**：mid/leaf 在依赖就绪前按 restart=any
   重启（ord1 中 mid 3 次启动/2 次死亡、leaf 4/3），全部在 ~20s 内收敛，部署成功。
   **崩溃发生在切流前不进入观察窗计数**（`crashWindowStart = max(release_start, first_healthy)`），
   这正是 ord1 能成功的原因。
3. **健康门是整组「与」+ 瞬时抽样**：引擎要求**所有**服务的目标版本任务 running ≥ replicas
   且 updateState completed 才切流（`releasing.go:68-118`）；但判定是每拍抽样，崩溃循环服务
   在其任务恰好 running 的瞬间可让健康门通过（对照样本中 healthy 发生在 58s，bad 已在重启
   循环；主样本则在 8s 即通过——两次都被观察窗拦下）。
4. **观察窗有两条独立安全网**：切流后崩溃 ≥2 次 → `E_OBSERVE_CRASH_LOOP`（对照样本实测）；
   running < desired 持续 ≥`ReplicasBelowFor` 或窗末不足 → `E_OBSERVE_UNHEALTHY`（主样本
   实测）；两者都以 verdict=unstable、app degraded 收场，不建新 deployment、失败服务留在原地
   （不静默清零）。单次退出且窗末恢复 → `W_DEPLOY_INSTABILITY` 警告通过。
5. **`depends_on: service_healthy` 的真实需求现状**：compose 解析期硬拒
   （`E_COMPOSE_UNSUPPORTED`，点名 path）；平台唯一的「先于长驻服务」排序原语是
   **init job（T1-3，`fleetly.job: init`：迁移先于新代码，失败即发布失败）**；运行期服务间
   依赖只能靠应用侧重试/自愈。

### 4.4 对设计的影响（确认 / 修正建议）

- **对 messageloop（redis→messageloop→mlbridge）**：不要依赖平台顺序。mlbridge 连不上
  redis/后端时应**重试而非退出**（或退出的重试间隔要保证「切流后窗内退出 <2 次」）；
  否则首次发布可能以 `E_OBSERVE_CRASH_LOOP`/`E_OBSERVE_UNHEALTHY` 失败。T1-5 割接时建议：
  mlbridge 的连接失败走有界重试 + 日志，不做 fail-fast 退出；redis 无健康依赖关系
  （同 app 并行起）在秒级内通常先就绪（本 spike base 就绪 ~9.5s 的设定偏保守）。
- **对 torchwood（postgres→server→worker/dispatcher）**：**迁移顺序由 init job 承担**
  （T1-3 已实现，这是 `depends_on` 唯一真正不可替代的需求）；DB 连接由 server/worker
  自身重试（torchwood 侧已有重连语义）；DT-8/DT-9 把 postgres 落托管实例后，PG 不再与
  server 同栈竞速，剩余 redis 依赖属重试域。T2-4 割接前建议在 torchwood 仓库核对
  server/dispatcher 的重试间隔，并把它记进割接 runbook。
- **文档建议**：把「切流点起算的崩溃计数 + 默认 60s 观察窗」的用户可见语义写进部署
  文档（首次发布含 fail-fast 依赖时可能以 `E_OBSERVE_CRASH_LOOP` 失败，属设计行为而非事故）。
- **平台不改**：不建议为 `depends_on` 开口子（现有拒绝口径 + init job 组合已覆盖真实需求；
  运行期依赖顺序不是平台能可靠提供的语义）。

### 4.5 不确定性

- 单节点 dind（调度无分布时延）；**加速参数（observe 5s / replicas_below 5s）与平台默认
  （60s / 10s）不同**——ord2 的「先误过健康门、观察窗兜底」路径在默认参数下需要复核：
  观察窗更长时，崩溃 ≥2 次更容易触发（检测更强），但「健康门瞬时通过」的窗口也更长；
  建议 staging 按默认参数复跑 ord1/ord2。
- 两次复跑的失败码不同（UNHEALTHY vs CRASH_LOOP）与健康门放行时点（8s vs 58s）不同，
  是抽样式健康门与重启状态竞速的结果（机制已由源码确认：`countNewRunning` 按拍抽样、
  两条观察窗判据独立）；多节点/负载下时序会不同，单次时序不可外推。
- 快照 1s 粒度，事件解析为 ms 级；`deploy rc-wall-s` 为秒级墙钟（仅参考）。

## 7. 发现的产品缺陷 / 挂账

**未发现必须修的产品缺陷（本票零产品代码改动）。** 以下为记录/挂账项：

1. **（文档挂账）`E_OBSERVE_CRASH_LOOP` / `E_OBSERVE_UNHEALTHY` / `W_DEPLOY_INSTABILITY`
   的用户可见语义未成文**：崩溃计数从切流点起算、默认观察窗 60s；含 fail-fast 依赖的
   首次发布可能因此失败。建议在部署文档/错误码文档补一段（设计行为，非缺陷）。
2. **（观察，不修）健康门的瞬时通过性**：崩溃循环服务可在任务恰好 running 的抽样瞬间
   通过整组健康门（对照样本实测 healthy@58s；主样本 8s），由观察窗两条判据兜底。机制来自
   `countNewRunning` 的按拍快照；若要更强，可讨论「健康门增加连续 N 拍」语义，但那是设计
   变更，不在本票。
3. **（边界记录）生产 resolver 只讲 HTTPS**：对纯 HTTP 私网 registry（本轮 `registry:2`
   无 TLS）解析失败，错误清晰（`server gave HTTP response to HTTPS client`），随后回落
   本机 inspect/最终 `E_IMAGE_PULL_FAILED` 点名原因。平台设置面不校验 registry scheme；
   若要支持 HTTP 私网 registry 需显式 opt-in（T1-2/T2-1 的文档面，非缺陷）。
4. **（环境事实，影响平台判定口径）containerd image store 下，swarm agent 拉取的镜像不出现
   在 `docker image ls`**（run `20260927-124508-s2-dind`：两节点 image ls 为空而任务 Running）；
   而按 digest 引用 `docker image inspect` 在任务运行后可见（run `20260927-132411-s2-dind`：
   两节点 post-check 均返回镜像 ID）。→ 平台/运维的「本机镜像存在性」判定应走 inspect + digest，

5. **（探针侧小坑，仅记录）宿主 kill 不终止 dind 内进程**（spike/a #11 复现）：③ 首轮
